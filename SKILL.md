# Luna Swarm

Execute a repository task autonomously by decomposing it into the smallest coherent, independently verifiable slices. Implementation runs may use one to three independent builder candidates per slice, then select or synthesize one canonical result. They use isolated worktrees by default, or the orchestrator worktree with collision-free concurrent ownership. Full implementation mode uses gated build, review, and repair roles. Simple implementation mode keeps only the slice-builder role. `review_mode: true` is a stricter review-only preset of simple mode: it keeps only the slice-reviewer role, uses one shared immutable snapshot, permits no authored source changes, and confines write-producing checks to disposable verification worktrees.

## Non-negotiable operating model

- The invoking parent thread is the orchestrator. Read [references/runtime-translation.md](references/runtime-translation.md) before judging parent eligibility and use its normative recommendation for the detected host; never assume Sol across hosts. Inspect and record the host-reported parent model and effort. A verified runtime matching or stronger than that host recommendation marks the orchestrator-bypass approval slot `not_required`. If the runtime is below the recommendation, or the host cannot expose or verify it, state `actual: <model>, <effort>` or `actual: unknown` with the evidence and warn that orchestration, finding adjudication, merge control, and release gating may be weaker. That warning makes the orchestrator-bypass slot required, but does not require a separate exact-token reply. Resolve it through the two-slot approval gate below. Do not spawn a replacement orchestrator. Child runtime selections never change an already-running parent model or effort.
- The orchestrator owns the full task, dependency graph, file ownership, finding validation, merges, gates, evidence, retry accounting, and cleanup.
- After every required approval slot is satisfied, run autonomously without further routine wave, merge, review, or remediation approval checkpoints. Stop for an unsatisfied required orchestrator-bypass slot, missing approval of the current matrix version, an invalid entry-flag combination, a real permission/safety barrier, an unrecoverable repository or review-snapshot state, unavailable resolved model/effort, or the applicable retry hard stop: three unsuccessful same-role continuations in simple or review mode, or five unsuccessful remediation cycles for any enabled full-mode slice layer, wave integration, or final integration unit.
- Optimize for zero collision risk, not minimum agent count. A logical wave may contain 60–100 or more agents when the slices are genuinely independent.
- Resolve `review_mode`, `worktree_mode`, `simple_mode`, `best_of_n`, `slice_adversarial_review`, `wave_integrated_review`, and `pipeline_waves` before spawning any child or changing repository state. Apply only the explicit preset resolutions documented below; never silently repair or downgrade any other invalid combination.
- Before creating an implementation worktree or shared review snapshot, spawning a child, or editing tracked source, present the user with a proposal that includes the mandatory deployment-wave matrix defined below. This is required for every run and every mode, including a one-wave simple-mode or review-only run.
- Never replace an agent thread silently. Before spawning any replacement because the original thread is technically unavailable, surface a user-visible notice stating the run, wave, slice, original role and thread identifier, exact evidence of unavailability, replacement role and runtime, and unchanged bounded scope. Record the notice and replacement relationship in `state.jsonl`. This disclosure is informational rather than an approval checkpoint unless the replacement changes authority, scope, permissions, workspace policy, or another user-controlled choice.
- When `pipeline_waves` is enabled, start any later-wave slice as soon as its declared dependencies are accepted and its writable files and mutable resources do not collide with active work; it need not wait for unrelated earlier-wave slices or reviews. When disabled, finish and accept the current wave before starting the next. Simple mode keeps one primary child role: slice builder in implementation mode or slice reviewer in review mode. Clarifying, resuming, or directing the same primary-role agent to complete its bounded work is permitted continuation, not a prohibited follow-up role.
- In `isolated_worktrees` mode, “land” means the orchestrator merges the accepted slice branch into the branch currently checked out in the orchestrator worktree. Only the orchestrator merges. In `same_worktree` mode, builders never stage or commit; the orchestrator alone stages each exclusive allowlist and creates the slice commits after builder completion and verification.

## Negative-scope contract

Treat every explicit user prohibition and non-goal as an acceptance constraint, not advisory prose. This includes instructions such as no fallbacks, compatibility paths, defensive measures, speculative hardening, extra validation, retries or recovery, silent defaults, catch-and-continue behavior, extra configuration, abstractions, tests, documentation, or other scope expansion.

- Extract the exact negative constraints before planning and attach the applicable subset to every matrix row and child packet. Preserve the user's wording when a paraphrase could weaken it.
- Negative constraints bind builders, reviewers, fixers, remediation roles, escalations, and the orchestrator. Generic best practices, reviewer preference, or a desire to make code “more robust” never overrides them.
- Do not add prohibited machinery because it might help a hypothetical caller, environment, migration, failure, or future requirement. The absence of behavior the user explicitly excluded is not a defect.
- A reproducible defect within supported behavior and authorized scope is an ordinary bug, not speculative hardening. A reviewer may report it but remains read-only. The orchestrator may validate it and authorize the smallest bounded repair through the separate fixer in full mode or the selected builder continuation in simple mode, even when that repair uses a guard or validation, provided it does not expand the supported contract or add alternate fallback behavior.
- Classify a proposal as hardening rather than a bug fix when it adds support for new inputs or environments, fallback/retry/recovery behavior, compatibility machinery, silent degradation, or another contract expansion. Reject it when barred by the negative constraints.
- Pause for user direction only when a validated defect cannot be repaired within the existing supported behavior, writable scope, and negative constraints, or when the user specifically prohibited the exact mechanism required. Surface the exact conflict and evidence; do not implement the disputed expansion or obtain it indirectly through a reviewer finding.
- Before accepting a candidate, fix, remediation, wave, or final result, inspect the live diff against every applicable negative constraint. Any violation is unacceptable until the unauthorized machinery is removed. Do not waive it because tests pass or the addition seems harmless.
- Reviewers must actively identify changed code that violates a negative constraint and frame the repair as removal or reduction to the smallest allowed behavior. They must not recommend new behavior outside the slice contract. A proposed finding is invalid unless it is grounded in an explicit requirement, governing repository rule, or reproducible defect within the authorized behavior and supported inputs or environments.
- Fixers receive the same negative constraints and make the smallest edit that resolves the validated finding. They may not replace removed fallback or speculative defensive machinery with a different mechanism that preserves the same prohibited behavior.
- Unless the user explicitly requests test creation or modification in the current task, add `no test creation or modification` to every implementation and review contract. This default prohibition covers test files, fixtures, snapshots, mocks, harnesses, test-only helpers, and test configuration.

## Entry flags

Resolve the operating flags below independently from runtime settlement and the approval slots:

- `review_mode: true | false`; default to `false`.
  - `false`: use the implementation workflow in this file.
  - `true`: before planning or execution, read and follow [references/review-mode.md](references/review-mode.md) completely. That reference defines the review-only lifecycle and replaces every implementation-only builder, writable-file, worktree, dirty-worktree, gate-repair, merge, commit, deployment, final-review, and cleanup instruction in this file where they conflict.
  - `review_mode: true` deterministically resolves `simple_mode` to `true`, even when `simple_mode` was omitted or explicitly requested as `false`. This is the preset's defined behavior, not a silent repair. Surface and record both the requested and resolved values.
  - In review mode, implementation `worktree_mode` is not executed. Surface and record any requested value, resolve it to `not_applicable(review_mode)`, and use the reference's single `shared_review_snapshot` workspace policy.
- `worktree_mode: isolated_worktrees | same_worktree`; default to `isolated_worktrees`.
  - This flag controls implementation runs only.
  - `isolated_worktrees`: use the normal per-slice branch and worktree workflow.
  - `same_worktree`: complete the implementation plan and ownership map before any child spawn or edit. Concurrent slices must have pairwise-disjoint writable files and mutable resources; serialize slices that overlap.
  - In `same_worktree`, all builders edit the orchestrator worktree. Builders must not stage, commit, merge, rebase, switch branches, or manipulate the Git index. The orchestrator waits for the relevant active builders, verifies ownership and gates, then stages and commits only the exact allowlist for each accepted slice.
- `simple_mode: true | false`; default to `false`.
  - `false`: run the full builder and final-review workflow, plus the slice and wave review roles enabled by the controls below and their associated fixer, remediation, and escalation roles.
  - `true` with `review_mode: false`: use only the slice-builder role. Spawn no adversarial, overengineering, style, post-fix, remediation, integrated-wave, final-task, fixer, or escalation roles. This restricts agent roles, not communication or continuation with a builder. The orchestrator may answer questions, clarify planned paths and dependencies, correct factual packet errors, wait for a planned dependency, send follow-up instructions, resume or reuse the selected builder thread, and direct that builder to repair its own slice within the authorized write allowlist and rerun checks. Prefer the selected builder (the sole builder when `best_of_n: 1`); if it is technically unavailable, a replacement may be spawned only in the same slice-builder role with the same bounded scope and only after the mandatory user-visible replacement disclosure. Do not terminate unrelated builders merely because one builder pauses, refuses, or reports a resolvable blocker. The orchestrator still verifies the live diff, exclusive ownership, required checks, and accepted commits or merges, and applies the resolved `pipeline_waves` policy.
  - `true` with `review_mode: true`: use only the slice-reviewer role and the review-mode reference. The reviewer may be clarified, resumed, or reused, but neither it nor any other child may fix code.
  - Reject `simple_mode: true` combined with `overengineering_review: true` or `style_review: true`. Do not silently ignore incompatible review toggles.
- `slice_adversarial_review: true | false`; defaults to `true` in full implementation mode.
  - `true`: include the normal adversarial review layer for every implementation slice.
  - `false`: omit that layer and all of its conditional fixer, post-fix reviewer, and escalation coordinates. This does not disable separately enabled overengineering or style layers.
  - In simple or review mode, record any requested value and resolve it to `not_applicable(simple_mode)` or `not_applicable(review_mode)` respectively. Review mode still performs its own required review-only slice pass under [references/review-mode.md](references/review-mode.md); this implementation flag does not control that lifecycle.
- `wave_integrated_review: true | false`; defaults to `true` in full implementation mode.
  - `true`: run the normal fresh integrated reviewer and review-driven remediation loop after each wave.
  - `false`: omit every wave integrated-reviewer coordinate and do not initiate remediation from an independent wave-review finding. Required integration gates, orchestrator verification, and bounded remediation of actual gate failures remain mandatory. Record the wave review result as `not_run_by_design(wave_integrated_review:false)` and do not claim an independently reviewed wave.
  - In simple or review mode, record any requested value and resolve it to `not_applicable(simple_mode)` or `not_applicable(review_mode)` respectively.
  - Neither this flag nor `slice_adversarial_review` controls the final integrated-task reviewer, which remains mandatory in full implementation mode.
  - Reject explicitly empty, non-boolean, or otherwise malformed values for either review flag.
- `pipeline_waves: true | false`; defaults to `true` in implementation mode.
  - `true`: start dependency-ready, collision-free later-wave slices without waiting for unrelated earlier-wave work to finish.
  - `false`: preserve a strict barrier between logical waves.
  - If earlier-wave remediation changes a dependency already consumed downstream, pause the affected downstream slices and rebase or revalidate them against the repaired dependency before integration.
  - In review mode, record any requested boolean value and resolve it to `not_applicable(review_mode)`.
  - Reject explicitly empty, non-boolean, or otherwise malformed values.
- `best_of_n: 1 | 2 | 3`; default to `1`.
  - This flag controls only the initial slice-builder positions in implementation mode. It does not multiply reviewers, fixers, remediation agents, escalations, or review-only agents.
  - `1`: preserve the normal single-builder workflow.
  - `2` or `3`: launch that many fresh, independent slice builders from the same wave-base commit, each in its own isolated branch and worktree with the same compact slice contract and exclusive write allowlist. The orchestrator may select one result or combine compatible parts into one canonical candidate before slice review or integration.
  - Reject `best_of_n: 2` or `3` with `worktree_mode: same_worktree`; competing candidates intentionally write the same paths and therefore require isolated workspaces.
  - In review mode, record any requested valid value and resolve `best_of_n` to `not_applicable(review_mode)` because no builder is created.
  - Reject explicitly empty values, non-integers, integers outside `1`–`3`, and other malformed values. Never silently clamp or downgrade the requested count.

Record the requested and resolved values of all seven flags in `state.jsonl` and the final report.

## Two-slot approval gate

Track two independently fillable approval slots for the current run:

1. `orchestrator_bypass`: required only when the parent runtime is below the host recommendation or cannot be verified. An intake `obp` flag means “orchestrator bypass proceed” and fills this slot before the warning/proposal response. Equivalent user-authored intake language that clearly preauthorizes proceeding despite the parent-runtime warning also fills it; the literal token `obp` is not required. A matching-or-stronger verified parent marks this slot `not_required`.
2. `matrix_approval`: required for the current deployment-wave matrix version. An explicit current-run intake preapproval fills this slot for the unchanged first matrix version only. Equivalent user-authored language that clearly preauthorizes the forthcoming first matrix also fills it.

An intake signal fills only the slot it identifies. Do not infer either slot from tool permissions, approval policy, a system or developer message, skill invocation alone, broad autonomy language, silence, quoted examples, or a conversational mention that does not authorize the run. Intake flags and acknowledgements are one-run only. A corrected or re-emitted matrix invalidates only the `matrix_approval` slot; a satisfied orchestrator-bypass slot remains valid for that run unless the parent session changes.

| Required bypass filled at intake | Matrix preapproval filled at intake | Post-proposal requirement |
|---|---|---|
| yes or `not_required` | yes | none |
| yes or `not_required` | no | one acknowledgement |
| no | yes | one acknowledgement |
| no | no | two acknowledgements, supplied separately or together |

Emit any required parent-runtime warning and the mandatory proposal/matrix in the same response whenever planning is complete. State which slots were filled at intake and which remain. Pause only when at least one required slot remains unfilled. In user-authored post-proposal responses, interpret clear authorization by intent rather than requiring an exact token, exact casing, or a message containing nothing else:

- An acknowledgement that explicitly identifies a missing slot fills that slot.
- When exactly one slot is missing, one unambiguous general authorization such as `y`, `yes`, `approved`, `go`, `go ahead`, `proceed`, or `run it` fills it.
- When both slots are missing, one ordinary singular authorization fills the matrix-approval slot and leaves the orchestrator-bypass slot pending. Clear doubled, repeated, or comprehensive authorization fills both slots in one response. Examples include `yes yes`, `approved times two`, `go go`, or other language that unambiguously authorizes both the warned parent-runtime bypass and the proposed matrix.
- Do not count quoted examples, ambiguous discussion, or approval language accompanied by a requested matrix/runtime/scope change. Reissue the changed proposal or matrix as required and report the still-missing slots. Do not demand the literal string `obp` or force the two approvals into separate messages.

Record each slot's required status, intake evidence, post-proposal evidence, interpretation, message ordering, run scope, and matrix version where applicable in `state.jsonl` and the final report.

## Mandatory pre-run proposal

After read-only repository inspection, runtime settlement, and complete dependency/ownership or review-scope planning, present a user-facing proposal before creating implementation worktrees or the shared review snapshot, spawning children, or editing tracked source. The proposal must always include a Markdown deployment-wave matrix, even when the plan has only one wave or one slice. In review mode, use the mode-specific matrix in [references/review-mode.md](references/review-mode.md).

Use one matrix row per planned slice and include at least these columns:

| Wave | Slice / gate | Depends on | Objective | Exclusive writable files | Workspace | Runtime placements | Review sequence | Gates / acceptance |
|---|---|---|---|---|---|---|---|---|

- List every planned deployment wave in dependency order and group rows by wave ID.
- Include one row for every implementation slice, an explicit wave gate row for every wave, and an explicit final integrated-reviewer gate row. When `wave_integrated_review` is disabled, its wave gate row must show `not_run_by_design(wave_integrated_review:false)` and no integrated-reviewer runtime rather than disappearing. Do not bury a run-level reviewer in an unrelated slice row. Conditional slice-local fixer, post-fix, remediation, and escalation coordinates may remain enumerated in their owning row's runtime cell.
- Use exact slice IDs, exact repository-relative writable paths, explicit dependency IDs, and the applicable negative constraints in each row's gates/acceptance cell. Write `none` when a cell has no value; never omit a required column.
- State the resolved `review_mode`, `worktree_mode`, `simple_mode`, `best_of_n`, `slice_adversarial_review`, `wave_integrated_review`, `pipeline_waves`, runtime placements, other review toggles, and any shared mutable-resource or snapshot isolation immediately before or after the matrix.
- On the first implementation matrix, when the complete planned writable scope contains only documentation, prose, prompts, policy, or non-executable metadata and no source, test, build, migration, script, generated, or other executable code, always show a visible `Recommendation: simple_mode: true` with the reason that the task is non-code-only and does not need the full follow-up-role pipeline. This is advice, not flag resolution: preserve and display any explicit user choice, never silently enable simple mode, and still show the recommendation when the user explicitly selected `simple_mode: false`. If any writable path contains code or the classification is genuinely uncertain, omit the recommendation rather than guessing. Do not repeat it on later matrix versions unless the planned scope newly changes from code-touching to non-code-only. Review mode already resolves simple mode to `true` and does not need this additional recommendation.
- Give every planned or conditional child spawn a stable coordinate using `<wave>/<slice-or-gate>/<role>/<occurrence>`, such as `W01/S03/builder/1`, `W01/S03/builder/2`, `W01/S03/adversarial-reviewer/1`, `W01/S03/review-fixer/1`, `W01/integrated-reviewer/1`, or `FINAL/integrated-reviewer/1`. When `best_of_n` is greater than `1`, the builder occurrences are competing candidates and the matrix must enumerate all of them plus the orchestrator-owned candidate-selection or synthesis gate. The runtime cell must enumerate every builder, enabled review-layer occurrence, conditional fixer/post-fix occurrence, remediation role, retry escalation role, enabled integrated-wave reviewer, and final reviewer that the row can deploy. Omit coordinates disabled by either review flag and show the disabled result explicitly in the review-sequence or gate cell. For full mode, predeclare the initial review or gate plus all conditional coordinates for cycles 1–5 for every enabled slice layer, every wave integration unit, and the final integration unit; never invent a sixth cycle after approval.
- For each coordinate, show the canonical roster default, `assignment_source` (for example `pool:<id>` or `direct:<coordinate>`), host, resolved model and effort, `selection_source` (`roster_default`, `translation_guide`, or `user_selected`), translation class (`exact`, `vetted_role_equivalent`, `user_selected_nondefault`, or `unresolved`), and translation-guide version. A matrix containing an `unresolved` runtime is informative only and cannot be approved for execution.
- A user may request a model for any assignable coordinate, explicit set of coordinates, role, slice, wave, or all remaining occurrences before or after a matrix is proposed. A model-only request uses the approved translation guide to resolve effort. Ask for clarification only when the target or requested setting is genuinely ambiguous. Never silently broaden a request to positions the user did not identify.
- Any user runtime request or change after matrix emission invalidates that matrix version and every approval or pre-approval associated with it. Keep execution paused while runtime choices are discussed. After every affected position is concrete and the user has no unresolved runtime request, re-emit the complete affected matrix and require a new post-emission approval. Runtime discussion, a change request containing approval language, and approval sent before or alongside the settled matrix never authorize execution.
- A runtime change during execution applies only to unstarted positions. For an active or completed position, surface that it cannot change retroactively and require explicit replan authority before restarting or repeating work. Re-emit and reapprove the complete remaining-wave matrix before any affected unstarted position proceeds.
- In `same_worktree`, require `best_of_n: 1` and use the matrix's writable-file column to show which overlapping slices will be serialized; only concurrently active slices require disjoint writable paths.
- Treat every emitted matrix version as an approval checkpoint under the two-slot gate. Before creating a worktree or shared review snapshot, spawning a child, editing, staging, committing, merging, or otherwise executing that matrix, ensure its `matrix_approval` slot and any required `orchestrator_bypass` slot are both satisfied. A qualifying intake preapproval may satisfy only the unchanged first matrix version. Identify filled and missing slots next to the emitted matrix. If all required slots are already filled, no additional pause is required. Otherwise hard-pause and apply the flexible post-proposal acknowledgement rules above. Any user-requested matrix/runtime/scope change invalidates the matrix slot, requires a corrected complete matrix, and requires new version-specific approval; it does not silently clear a run-scoped orchestrator-bypass approval.
- If planning changes before the first spawn, emit the corrected complete matrix and obtain its approval before execution. If a boundary violation or integration finding changes future waves during execution, update and re-emit the complete remaining-wave matrix and obtain its approval before deploying the affected wave.

Record proposal emission, the current matrix version, both approval-slot states, the qualifying user-authored intake and/or post-proposal evidence, its ordering and interpretation, and the exact approved version in `state.jsonl`. Do not claim that implementation or review execution started before every required slot has evidence.

## Runtime positions and default roster

In full implementation mode, use a new agent thread for every role, builder candidate, and retry. Never reuse a builder as a reviewer or fixer, never resume an earlier role thread, and never pass one agent's hidden reasoning to another. In simple implementation mode, use only the slice-builder row; `best_of_n` may create multiple initial occurrences of that same role, but only the selected builder may be continued afterward. In review mode, use only the configured or default slice-reviewer pools in the review-mode reference. Same-role clarification and continuation are allowed in either simple branch; do not create a different follow-up role.

Before resolving child runtimes or emitting a matrix, read and follow [references/runtime-translation.md](references/runtime-translation.md) completely. Its dated mappings are operational role equivalents, not claims that different models are identical.

| Role | Canonical default model and effort | Workspace |
|---|---|---|
| Slice builder | Luna Max (`gpt-5.6-luna`, `max`) | Its resolved slice workspace |
| Slice adversarial reviewer | Fresh Luna Max | Slice workspace, review-only |
| Slice overengineering reviewer, when enabled | Fresh Luna Max | Slice workspace, review-only |
| Slice style reviewer, when enabled | Fresh Luna Max for every occurrence | Slice workspace, review-only |
| Slice review-layer fixer | Fresh Luna Max | Slice workspace |
| Post-fix layer reviewer | Fresh Luna Max | Slice workspace, review-only |
| Non-escalated remediation fixer/reviewer | Fresh Luna Max | Its resolved remediation workspace |
| Integrated wave reviewer | Fresh Sol XHigh (`gpt-5.6-sol`, `xhigh`) | Orchestrator branch, review-only |
| Final integrated-task reviewer | Fresh Sol XHigh (`gpt-5.6-sol`, `xhigh`) | Orchestrator branch, review-only |
| Escalated builder after retry 3 | Fresh Sol High (`gpt-5.6-sol`, `high`) | The affected workspace |
| Escalated reviewer | Fresh Sol XHigh (`gpt-5.6-sol`, `xhigh`) | The affected workspace, review-only |
| Escalated fixer | Fresh Sol XHigh (`gpt-5.6-sol`, `xhigh`) | The affected workspace |

- Defaults apply per runtime coordinate, not through a global power tier. There is no global or categorized child-runtime override.
- In review mode, `review_agents` supplies additional eligible runtime pools; it never replaces the canonical Luna Max pool by itself. Keep Luna Max for a reviewer coordinate unless the orchestrator determines from the concrete slice demands that a supplied option is likely to produce a better outcome. Do not assign supplied options merely because they were listed or have unused capacity. A direct, coordinate-specific user instruction remains an explicit selection and is handled separately under the rules below.
- Keep runtime selection and assignment provenance separate. `selection_source` records how the model/effort was selected (`roster_default`, `translation_guide`, or `user_selected`); `assignment_source` records how the coordinate was assigned (for example `pool:<id>`, `direct:<coordinate>`, or `role_default:<role>`). Never overload one field with the other.
- A user's explicit coordinate-specific or scope-specific runtime choice takes precedence over the roster and translation guide only for the positions the user identified. Record the raw request and every affected coordinate.
- If the user supplies only a model, use the translation guide's role-specific effort for that model and host. Preserve an explicitly supplied effort.
- If a requested or guide-resolved model/effort pair is unavailable, surface exact evidence and keep the position `unresolved`; do not substitute. The user may choose another runtime, after which the settled matrix must be re-emitted and newly approved.
- If an explicit spawn interface exposes model and effort, pin both to the matrix-approved values. If the launcher cannot honor the approved model or effort, do not start that position.
- Full-mode fresh-role requirements prohibit reused contexts. Simple-mode builder continuation should resume or reuse the builder's existing context when possible and retain the runtime approved for that same builder coordinate.
- A role-, slice-, or wave-scoped runtime request for the initial builder applies to every affected `best_of_n` candidate unless the user explicitly targets individual builder coordinates. Candidate count does not change runtime selection rules.
- Retry counting, role changes, and the escalation boundary remain mandatory. Each ordinary retry and escalation role uses its own matrix-approved coordinate rather than inheriting a power category.

All child coordinates inherit the parent or launcher's default speed behavior; do not preflight, record, or separately approve speed.

## Protect child context

The orchestrator retains global context. Child agents receive only the smallest full-fidelity packet needed for one role on one slice.

- Do not paste the global task, the full plan, the full ledger, unrelated requirements, source files, large diffs, raw logs, prior transcripts, or another agent's reasoning.
- Point to live repository paths, exact symbols, commits, commands, and compact receipt files instead of copying their contents. Necessary broad read context is allowed through exact paths and symbols.
- Give one agent exactly one role and one bounded objective.
- A builder receives only its objective, exclusive write allowlist, applicable negative constraints, the orchestrator-validated atomicity proof when a multi-file exception applies, necessary interface/dependency facts and exact read paths/symbols, acceptance criteria, repo instructions/gates, base commit, and receipt format.
- A reviewer receives the same compact slice contract including negative constraints, the rubric for exactly one active review layer, and the live commit/diff to inspect. It does not receive the builder transcript or another layer's reviewer transcript.
- A fixer receives only orchestrator-validated findings from one active review layer with their evidence and the slice contract including negative constraints. It does not receive the raw reviewer transcript, rejected findings, or another layer's findings.
- A post-fix reviewer receives the live fixed state, slice contract including negative constraints, and the same active-layer rubric, not the fixer transcript.
- Agent responses must be concise factual receipts. Exact headings, field order, and prose format are not acceptance requirements. Keep full command output on disk only while needed; return command, exit status, and the smallest decisive excerpt or path.
- Broad reads do not expand the writable allowlist or invalidate a one-file slice. Supply enough exact-path and symbol context for the child to perform its bounded role correctly.

Every child packet must include this compact contract, expressed without duplicating already supplied fields:

1. Read and obey applicable `AGENTS.md` and repository-local instructions.
2. Work only in the supplied workspace and base state.
3. Modify only the exclusive write allowlist. Reading other files is allowed when necessary.
4. Preserve unrelated work. Do not merge, rebase, switch branches, broaden scope, or edit shared files not assigned to this slice.
5. Obey every supplied negative constraint literally. Do not add or recommend a fallback, speculative defensive measure, hardening, compatibility behavior, test change, or other excluded work. A guard or validation is allowed only as the smallest bounded repair for an orchestrator-validated reproducible defect within supported behavior, and only when it adds no fallback or contract expansion. Otherwise stop and report the exact evidence instead of implementing or proposing it.
6. Run the specified checks and report any failure with decisive evidence; do not silently waive it.
7. In `isolated_worktrees`, commit implementation/fix work before reporting. In `same_worktree`, never stage or commit; the orchestrator owns the Git index and commits. Reviewers make no code changes.
8. If another file must change, pause and report the exact boundary violation to the orchestrator; do not expand ownership yourself. Remain available for the orchestrator to clarify the existing plan or resume the work after it safely revises ownership and dependencies.
9. Return a concise receipt containing status, commit when applicable, files changed or findings, checks/evidence, and blockers. Labels and ordering may vary.
10. In simple mode, treat an uncertain path, a not-yet-visible but planned destination, a dependency timing issue, or another resolvable packet ambiguity as a request for orchestrator clarification, not as a terminal refusal. Continue in the same builder role when the orchestrator responds. Broad read context may be supplied through exact paths and symbols without changing the one-file writable slice.

## Initialize the run

1. Confirm this is a Git repository and record:
   - original branch and `HEAD`;
   - repository root and Git common directory;
   - applicable `AGENTS.md` files and repository-defined build, test, lint, formatting, review, and commit rules.
2. Inspect the detected host and parent orchestrator's host-reported model/effort, then apply the parent-runtime eligibility table in [references/runtime-translation.md](references/runtime-translation.md). Mark the orchestrator-bypass slot `not_required` for a verified runtime matching or stronger than that host's recommendation. If it is below the recommendation or unavailable/unverifiable, emit the existing quality warning with `actual: <model>, <effort>` or `actual: unknown` and its evidence and mark that slot required. Detect any qualifying intake bypass flag or equivalent preauthorization, but do not pause yet when the proposal can be completed safely with read-only work. Record the detected host, recommendation, actual runtime, warning, slot state, intake evidence, and one-time current-run scope.
3. Resolve `review_mode`, defaulting to `false`, and validate `best_of_n` as an integer from `1` through `3`, defaulting to `1`. If review mode resolves to `true`, record the requested values, resolve `best_of_n`, `slice_adversarial_review`, `wave_integrated_review`, and `pipeline_waves` to `not_applicable(review_mode)`, read [references/review-mode.md](references/review-mode.md) completely, and follow its `R01`–`R08` lifecycle instead of steps 4–12 and the implementation `P01`–`P10` lifecycle below. If review mode resolves to `false`, resolve `worktree_mode`, defaulting to `isolated_worktrees`, `simple_mode`, defaulting to `false`, and `pipeline_waves`, defaulting to `true`; reject unknown values and reject `best_of_n` greater than `1` with `same_worktree`. In full implementation mode, resolve `slice_adversarial_review` and `wave_integrated_review` independently, defaulting each to `true`. In simple implementation mode, record any requested boolean values and resolve both review flags to `not_applicable(simple_mode)`.
4. Read the runtime translation guide and resolve every planned or conditional child coordinate from its canonical default, the detected host, and any user runtime requests. Keep unavailable, unsupported, or ambiguous positions `unresolved` instead of silently repairing them. Do not emit an executable matrix until every position is concrete.
5. Resolve the two additional per-slice review toggles from the invocation. Both default to off unless the invocation explicitly enables them:
   - `overengineering_review`: add an overengineering layer after adversarial review when that layer is enabled, or make it the first substantive layer when `slice_adversarial_review` is disabled;
   - `style_review`: add a style layer immediately after every substantive layer that runs.
   Reject either enabled toggle when `simple_mode` is `true`.
6. Record the exact per-slice layer sequence for the run. In simple mode it is builder only. In full mode, start with adversarial when `slice_adversarial_review` is enabled, append overengineering when enabled, and insert style immediately after each enabled substantive layer when `style_review` is enabled. If no substantive layer is enabled, require `style_review: false`, record `no independent slice review`, and accept a slice only from orchestrator diff/constraint verification and passing targeted gates without making a clean-review claim.
7. Do not start from a dirty orchestrator worktree. Never stash, reset, or overwrite unrelated user changes. Resolve task-owned changes into a safe starting commit when clearly authorized by the task; otherwise hard-stop with exact evidence.
8. Build the complete dependency DAG, ownership map, and per-slice negative-constraint map before execution. When `worktree_mode` is `same_worktree`, require `best_of_n: 1` and serialize slices with overlapping writable files or mutable resources.
9. Present the mandatory pre-run proposal and complete deployment-wave matrix. Verify that every planned slice, dependency, exclusive writable path, applicable negative constraint, workspace, initial builder-candidate coordinate, candidate-selection or synthesis gate when applicable, runtime coordinate and resolved assignment, review sequence, and gate appears in it. For each multi-file exception, also show the attempted dependency-ordered one-file plan and concrete atomicity proof. Resolve the orchestrator-bypass and matrix-approval slots under the two-slot gate: identify intake-filled and missing slots, skip an additional pause when all required slots are satisfied, or hard-pause once and accept flexible acknowledgement of one or both missing slots. Any runtime discussion or change requires the settled matrix to be emitted afterward and its matrix slot approved by a later message. Record proposal emission, matrix version, runtime-settlement evidence, both slot states and evidence, interpretation, and ordering before implementation begins.
10. Create one run-scoped temporary directory under the Git common directory, for example `<git-common-dir>/luna-swarm/<run-id>/`.
11. Maintain only two compact orchestrator artifacts during execution:

## Implementation-mode canonical orchestrator todo

When `review_mode` is `false`, follow these phases in order. Review mode uses the `R01`–`R08` lifecycle in its reference instead.

1. `P01` Initialize controls and ledger.
2. `P02` Inspect repository and instructions.
3. `P03` Plan dependencies and ownership, then emit the proposal and deployment-wave matrix.
4. `P04` Prepare the next wave.
5. `P05` Build slice candidates and select one result per slice.
6. `P06` Run enabled slice reviews and accept slices.
7. `P07` Merge and gate the wave.
8. `P08` Run enabled wave review and remediate integration or gate failures.
9. `P09` Run final gates and review.
10. `P10` Clean up and report.

Anti-drift rules:

- Keep one active phase in `state.jsonl`.
- Advance only from orchestrator-verified evidence.
- Do not advance from `P03` to `P04` until every runtime coordinate is settled, the complete deployment-wave matrix has been presented after the last runtime request or change, every required approval slot is satisfied, and all evidence, interpretations, versions, and ordering are recorded. Only an unchanged first matrix version may rely on intake preapproval; every changed or later version requires post-emission matrix approval. A run-scoped orchestrator-bypass approval remains satisfied unless the parent session changes.
- With `pipeline_waves: true`, advance dependency-ready collision-free slices from later waves while unrelated earlier-wave work continues. With `pipeline_waves: false`, loop from `P08` to `P04` only after the current wave is accepted.
- After interruption, resume from the ledger and recheck live Git state.
- Claim completion only when `P01` through `P10` are complete and nothing remains active or blocked.

## Decompose into collision-free waves

Build a dependency DAG before implementation.

- Define each logical wave as a useful grouping of dependency-ready slices whose concurrently active write sets and mutable resources are pairwise disjoint.
- Use a blocking slice or wave mainly to serialize shared-file or mutable-resource collisions or to land a changed contract required by downstream slices. After it is accepted, recompute readiness and form the next maximal collision-free wave.
- Default every authorized writable slice to exactly one file, including ordinary application code, configuration, migrations, manifests, and generated artifacts. Tests may enter writable scope only when the user explicitly requested test creation or modification. Reading other files is unrestricted when necessary.
- Before allowing a multi-file slice, construct and evaluate at least one dependency-ordered plan of one-file slices. Try compatibility-preserving intermediate steps where the repository permits them, such as introducing a new API or destination, migrating consumers, and only then removing the old API or source.
- “Atomic” means no ordering of separate one-file commits can keep every intermediate accepted repository state valid, testable under its required gates, and safely landable. Files are not atomic merely because they implement one feature, migration, refactor, final invariant, conceptual operation, or mutually refer to one another. Dependency coupling calls for ordered slices and blocking waves, not automatic bundling.
- Use a multi-file slice only after the orchestrator proves the one-file alternative fails. Record the attempted order, the exact intermediate compile, contract, generation, or required-gate failure, and why no compatibility bridge or different ordering resolves it. A conclusion such as “these files must stay consistent” is not proof.
- Split independently writable files into separate dependent slices whenever practical. Never bundle files for convenience, fewer agents, feature-level grouping, or to let one builder own an entire semantically coherent change.
- Assign an exclusive write set to every slice. Two concurrently active slices must never modify the same file, generated output, manifest, registry, migration, project file, shared test file, or other mutable resource.
- Assign every shared manifest, registry, migration, project file, generated output, or other shared file to one dedicated owner slice. Serialize it in a low-count or single-agent wave when it blocks other work.
- When the user explicitly requested test creation or modification, prefer a separate test slice when the test file can be changed and verified independently. Keep source and test files together only under the same recorded multi-file atomicity exception. A shared test file belongs to one slice only.
- Account for non-source collisions: build output directories, DerivedData, caches, ports, databases, simulators, generated files, and external mutable state. Give each worktree isolated paths/resources or serialize the affected slices.
- In `isolated_worktrees`, each slice branches from a recorded dependency-complete base commit; slices with the same accepted dependencies may share a base. In `same_worktree`, each slice records its dependency-complete comparison base while editing the orchestrator worktree.
- Maximize useful concurrency. If the runtime cannot open the full logical wave at once, schedule transparent batches. With `pipeline_waves: true`, later-wave slices may begin as soon as their dependencies are accepted and they do not collide with active work. With `pipeline_waves: false`, keep the same wave base and wait for the full wave to pass orchestrator verification, integration gates, and any enabled integrated review before beginning the next wave.
- Record the full DAG and ownership map only in orchestrator state. Each child sees only its slice.
- When `worktree_mode` is `same_worktree`, validate ownership before implementation and before each pipelined start. Writable paths need be disjoint only among concurrently active slices; serialize any overlap and record that dependency in `state.jsonl`.
- Make the user-facing deployment-wave matrix a faithful projection of the complete DAG and ownership map. Do not hide a planned slice, file, dependency, workspace, review layer, or gate from the matrix.
- For every proposed multi-file slice, show the attempted one-file landing order and atomicity proof immediately adjacent to its deployment-wave matrix row. If that proof is absent or only states semantic relatedness or final consistency, reject the multi-file slice and replan it as dependency-ordered one-file slices before spawning builders.

## Explicit-opt-in test rule

Never create or modify tests unless the user explicitly requests test creation or modification in the current task. Running existing tests and other required gates is still allowed.

- A request to implement, fix, refactor, validate, make production-ready, or satisfy existing checks does not imply permission to author tests. Repository convention, changed behavior, a bug fix, missing coverage, a coverage threshold, reviewer preference, or a desire for regression protection also does not grant that permission.
- Without an explicit test request, treat all tests, fixtures, snapshots, mocks, harnesses, test-only helpers, and test configuration as read-only. Plan no test slices, accept no test-related diff, and reject every reviewer finding or fixer proposal that would add or modify them.
- If an existing test or coverage gate fails, fix only the authorized production scope when that is correct. If the change genuinely requires a test modification or a repository rule requires new tests, stop and surface the exact conflict; do not edit tests or silently broaden scope.
- A reviewer may use existing tests as evidence but must not report missing coverage or absent regression tests as a finding unless the user explicitly requested tests. The orchestrator must reject such a finding rather than forwarding it to a fixer.
- When the user explicitly requests tests, use the smallest focused case and fewest assertions that decisively prove the requested behavior, reuse existing infrastructure, and follow normal ownership rules. Do not add speculative permutations, broad snapshots, helpers, fixtures, mocks, or harnesses beyond what that explicit request requires.
- Never delete or weaken existing tests, lower thresholds, skip mandatory checks, or game coverage metrics.

## Execute each build slice

For every slice in the wave:

1. In `isolated_worktrees`, create `best_of_n` uniquely named candidate branches and worktrees from the same wave-base commit. With the default `best_of_n: 1`, this is the normal single slice branch and worktree. In `same_worktree`, which requires `best_of_n: 1`, use the clean orchestrator worktree and create no slice branch or worktree.
2. Spawn every initial builder candidate in parallel as one candidate group, each in a fresh thread using its matrix-approved builder coordinate and the same compact slice packet. Candidates must not see another candidate's transcript, diff, branch, worktree, or receipt.
3. Wait for every candidate in the slice's candidate group, then independently verify each actual diff, owned-file compliance, negative-constraint compliance, required targeted gates, and receipt. In `isolated_worktrees`, also verify each commit. In `same_worktree`, verify that the single builder did not stage, commit, switch branches, or modify the Git index. Do not trust self-report alone.
4. When `best_of_n` is greater than `1`, compare candidates against the shared slice contract, negative constraints, repository rules, live diffs, and decisive gate evidence. Disqualify unauthorized scope or behavior. The orchestrator may select one candidate unchanged or choose a canonical candidate workspace and combine compatible parts from multiple candidates by cherry-picking or applying bounded diffs. Verify the synthesized result as a new whole against ownership, negative constraints, repository rules, and required gates; do not combine incompatible approaches merely to preserve work. Record the evidence and rationale. If no candidate or synthesis yields a safely reviewable in-scope result, accept none and apply the existing blocker or replan behavior.
5. After the canonical candidate is verified and essential receipts are recorded, discard every noncanonical candidate by removing only its exact run-created worktree and branch. Verify each removed path and branch belongs to this run and is not the canonical candidate or a preexisting resource. The canonical branch, worktree, commit, and selected builder context become the slice's sole state for later review, repair, integration, and simple-mode continuation.
6. When `simple_mode` is `true`, spawn no separate follow-up role. If the selected builder diff obeys every negative constraint and its gates are acceptable, mark the slice builder-accepted. Otherwise inspect the live state, resolve factual ambiguity, and send only the selected builder a targeted clarification, removal, correction, or repair request within its write allowlist and negative constraints. Resume or reuse that builder and re-verify its work under the simple-mode retry rule below. A builder question, pause, refusal based on a resolvable packet fact, incomplete first result, or initial gate failure is not by itself a hard stop. Continue to step 15 only after the slice is accepted or an actual hard-stop condition is reached. When `simple_mode` is `false`, use the invocation's recorded review-layer sequence against only the selected candidate. Run only enabled layers. Every occurrence, including both style occurrences when adversarial and overengineering are both enabled, is a separate layer with fresh agents and no reused context. If the sequence is empty, spawn no slice reviewer or review-driven fixer; accept the slice only when the selected candidate already passes orchestrator diff, ownership, negative-constraint, and targeted-gate verification, otherwise select no acceptable result and follow the existing blocker or replan path.
7. Apply the active layer's bounded rubric:
   - adversarial: first search the changed code for violations of the slice's negative constraints, including unauthorized fallback, speculative defensive or hardening behavior, compatibility or scope-expanding machinery, or test changes that were not explicitly requested, and report each concrete violation as a removal finding. Then search for requirement misses, correctness defects, regressions, architecture violations, security/performance issues reachable within authorized behavior and supported inputs or environments, documentation defects, and valid nits. Only when the user explicitly requested tests may missing requested coverage or requested changed behavior left unproven by tests become a finding. Do not turn a hypothetical unsupported state, excluded edge case, or default desire for tests into a finding;
   - overengineering: remain read-only and review only this slice, then:
     1. derive the minimum required behavior and smallest plausible implementation shape from the slice contract and negative constraints before reading code; treat a safeguard as required only when the contract, a governing repository rule, or a reproducible in-scope defect requires it;
     2. inspect only owned/changed files and necessary call sites;
     3. map each fallback, guard, validation, recovery path, compatibility branch, abstraction, helper, state machine, dependency, and file to an explicit requirement; any machinery barred by a negative constraint is a removal finding. For any multi-file slice, independently test the recorded one-file landing order and reject semantic relatedness or final consistency as atomicity proof;
     4. treat file count and LoC as signals only; report a finding only when concrete machinery can be removed or simplified while preserving required behavior, negative constraints, contracts, and gates;
     5. treat required error handling, concurrency, recovery, boundaries, and repository conventions as justified; begin neutral.
     Return `CLEAN` or evidence-backed findings naming the mechanism, exact evidence, smaller replacement, and requirements preserved. Exact formatting is optional;
   - style: actively check the changed code against applicable `AGENTS.md`, repository format and lint rules, established local conventions, and any explicit style directives in the invocation. Do not invent personal-preference findings without a concrete governing convention.
8. Spawn a fresh specialist reviewer using the runtime approved for that slice's active review-layer coordinate in the selected candidate's resolved slice workspace. It returns only evidence-backed findings within that layer's rubric or `CLEAN`.
9. The orchestrator validates every finding against the negative constraints, live code, executable behavior, or the active layer's governing evidence. Validation requires a violated negative constraint, explicit requirement, governing repository rule, reproducible in-scope code path, exact file/symbol, failing command, removable concrete complexity, violated style rule or local convention, or other logically decisive proof. Vague possibility, hypothetical unsupported state, generic hardening advice, or preference is not enough.
10. Reject unsupported or scope-expanding findings with a one-line evidence-based reason. A reviewer request for prohibited fallback or speculative defensive behavior cannot be laundered into authorized scope. A reproducible defect within supported behavior remains valid even when its smallest repair is a guard or validation; the reviewer still remains read-only and the authorized repair role performs the change. Every validated in-scope finding, including every valid nit, must be fixed; there is no severity threshold for acceptance.
11. When findings exist, spawn a fresh review-layer fixer using the runtime approved for that slice and layer's fixer coordinate in the selected candidate's workspace with only the active layer's validated findings, compact slice contract, and negative constraints. Require the smallest compliant change, preferring deletion when the finding is unauthorized machinery. Verify its diff, ownership, negative-constraint compliance, checks, and commit when applicable.
12. Spawn a fresh post-fix reviewer using the runtime approved for that slice and layer's post-fix-reviewer coordinate in the selected candidate's workspace. Repeat validation and fresh fixer/reviewer cycles only through the initial review plus five unsuccessful cycles; stop the run on the fifth unsuccessful cycle under the retry hard-stop rules.
13. After one layer is clean, advance to the next recorded layer and use entirely fresh agents. A clean style layer after adversarial review does not satisfy the later style occurrence after overengineering review.
14. If any agent discovers a needed edit outside the write allowlist, pause that slice and return control to the orchestrator; never permit opportunistic scope expansion. In full mode, recompute ownership/dependencies and redeploy fresh agents. In simple mode, first determine whether clarification of the existing planned mapping resolves the blocker. If the plan truly must change, recompute ownership/dependencies, preserve every collision rule, update and re-emit the affected deployment-wave matrix as required, then resume the selected builder thread with the corrected bounded packet. Use a replacement slice builder only if the selected thread is technically unavailable and only after the mandatory user-visible replacement disclosure.
15. In `same_worktree`, wait for all active builders and any enabled full-mode slice review/fix cycles to finish. Re-verify the complete live diff and exclusive ownership, stage only the exact allowlist for one accepted slice, commit it, and repeat per slice. Never use broad staging commands. If files overlap or the Git index contains unowned changes, hard-stop without committing.

In full mode, a slice is accepted only after any best-of-N selection or synthesis is complete, every noncanonical candidate has been discarded, every enabled review-layer occurrence has completed in order with zero orchestrator-validated findings, the canonical candidate's accepted commit changes only its owned files, every negative constraint is satisfied, and all applicable gates pass. When no slice layer is enabled, record `not_run_by_design(no_enabled_slice_review)` and do not call the slice independently reviewed or review-clean. In simple mode, a slice is accepted only when the canonical slice-builder work, including any permitted clarification and repair continuations, passes orchestrator diff, ownership, negative-constraint, and gate verification; no clean-review claim is made.

## Retry escalation and hard stop

Track retries independently for each bounded unit: every enabled full-mode slice review layer, every full-mode wave integration, and the final integration. Each unit has exactly one initial review or gate attempt followed by at most five unsuccessful remediation cycles. A cycle is unsuccessful only when its fresh post-fix review, enabled integrated review, or rerun gate still has an orchestrator-validated finding or required-gate failure; a clean or gate-passing result ends that unit immediately. An initial review or gate attempt does not count as a retry.

- Predeclare every conditional coordinate for the initial attempt and cycles 1–5 in the approved matrix. For each enabled slice layer, enumerate its reviewer, each possible fixer and post-fix reviewer, and the escalated builder/reviewer/fixer coordinates. For wave integration, enumerate gate-remediation coordinates for every possible cycle and enumerate integrated-reviewer occurrences only when `wave_integrated_review` is enabled. For final integration, enumerate the initial integrated reviewer, each possible remediation slice and fixer/reviewer or escalation coordinate, and the next final reviewer for every possible cycle. Do not invent an unlisted sixth cycle or conditional role after approval.
- In full mode, a retry is one completed fix-and-fresh-review cycle that still leaves a validated finding or required-gate failure. Receipt formatting never consumes a retry.
- In simple mode, a retry is one completed orchestrator-directed repair continuation by the selected slice builder that still leaves its bounded work unacceptable, violates a negative constraint, or leaves a required gate failing. A question, pause, blocker report, or refusal caused by missing or incorrect packet facts does not count as a retry until the orchestrator supplies the needed clarification and the builder has a fair opportunity to continue. Resume or reuse the selected builder at its matrix-approved builder runtime with the original negative constraints; if that thread is technically unavailable, a replacement may continue only as the same bounded slice-builder role and only after the mandatory user-visible replacement disclosure. Do not spawn a reviewer, fixer, remediation, or escalation role.

The escalation boundary changes roles, not a global power tier. Preserve retry rules and fresh-role boundaries, and use the separately approved runtime coordinate for every ordinary fixer, reviewer, escalated builder, escalated reviewer, and escalated fixer occurrence.

- Simple-mode retries 1–3 reuse or resume the slice-builder role at its matrix-approved builder runtime. The orchestrator supplies only verified corrections, clarified dependencies or destinations, validated repair instructions, and required checks. After each continuation, independently verify the live diff, ownership, and gates. Do not cancel other active, disjoint builders while this occurs. After the third unsuccessful repair continuation, stop scheduling dependent work, allow already-running disjoint builders to finish safely when doing so cannot worsen the state, then hard-stop with the exact evidence and preserved partial results.
- For each full-mode slice layer, run the initial layer reviewer, then cycles 1–3 with fresh ordinary fixer and post-fix reviewer coordinates. If cycle 3 is unsuccessful, cycles 4–5 use the predeclared escalation coordinates in the same resolved workspace: an escalated builder and reviewer, followed when needed by an escalated fixer and reviewer. Count each still-failing cycle once; do not add an extra retry for the escalation handoff.
- For each full-mode wave integration, run the initial integration gates and, when `wave_integrated_review` is enabled, the initial integrated reviewer, then at most five cycles. Each unsuccessful cycle consists of orchestrator-validated enabled-review findings or failed integration gates and bounded remediation in exclusive workspaces, followed by rerun gates and, only when enabled, a fresh integrated reviewer using that cycle's predeclared coordinate. Use ordinary remediation coordinates for cycles 1–3 and the approved escalation coordinates for cycles 4–5.
- For the final integration, run the initial final integrated reviewer, then at most five cycles with the same bounded remediation, full-gate rerun, and fresh final-review sequence. Use ordinary remediation coordinates for cycles 1–3 and the approved escalation coordinates for cycles 4–5.
- On the fifth unsuccessful cycle for any full-mode slice layer, wave integration, or final integration, hard-stop that swarm run. Do not waive findings, downgrade gates, expand ownership ad hoc, schedule a sixth cycle, or continue to later waves. Report the exact unit, cycle count, commits, evidence, remaining findings/failures, and current branch state.

## Land and review a full wave

1. Do not integrate an incomplete slice. With `pipeline_waves: false`, wait until every build slice in the logical wave is accepted before integration. With `pipeline_waves: true`, integrate each accepted slice in dependency-safe order as soon as doing so is needed to unblock a ready downstream slice; do not mark the wave accepted until all of its slices and gates are complete.
2. In `isolated_worktrees`, the orchestrator merges accepted slice branches into its current branch in dependency-safe order, following repository merge conventions. Before starting a pipelined dependent slice, verify its recorded base contains every required accepted dependency commit. In `same_worktree`, the orchestrator-created allowlist commits are already on the current branch. No child agent merges.
3. Verify each accepted commit is present, concurrent ownership remained disjoint, and repository-specified integration gates pass. Any failure blocks the affected integration unit and must be repaired or reported with decisive evidence; do not silently waive it.
4. When `simple_mode` is `true`, spawn no integrated reviewer or remediation role. On an integration-gate failure, identify the responsible owned slice or slices, give the selected owning builder threads the verified failure evidence and their negative constraints, and resume or reuse them to repair only their respective allowlists under the simple-mode retry rule. Serialize those continuations when integration safety requires it, then reintegrate and rerun the gates. Accept the wave only from orchestrator verification of the negative constraints and passing integration gates. Hard-stop only when an applicable retry limit or another defined terminal condition is reached. Then continue with the next wave. When `simple_mode` is `false` and `wave_integrated_review` is `true`, spawn a fresh reviewer using the runtime approved for that wave's integrated-reviewer coordinate over the fully integrated wave, comparing the current branch to the recorded wave base and checking the task requirements, negative constraints, and emergent cross-slice behavior. The reviewer is read-only, must reject speculative scope expansion under the slice-review rules, and returns only evidence-backed findings or `CLEAN`. When full mode has `wave_integrated_review: false`, spawn no integrated reviewer and record `not_run_by_design(wave_integrated_review:false)`; proceed to remediation only for an actual integration-gate failure.
5. Steps 5–9 apply only in full mode and only while an enabled integrated review has validated findings or an integration gate has failed. The orchestrator validates every reviewer finding and gate failure against live code/behavior and the negative-scope contract. Reject any finding that would introduce excluded behavior or expand scope. Every validated in-scope finding, nit, and task-caused gate failure must be fixed.
6. Partition validated findings or gate failures into the smallest remediation slices with mutually exclusive write sets. Findings or failures touching the same file belong to one remediation slice; use serial remediation waves when shared files or dependencies require it.
7. For each remediation slice in `isolated_worktrees`, create a separate worktree from the current integrated branch. In `same_worktree`, use the orchestrator worktree, require remediation write sets to be disjoint when run concurrently, and let only the orchestrator stage and commit exact remediation allowlists. Spawn a fresh fixer and then a fresh reviewer in the resolved remediation workspace, giving both the applicable negative constraints. Apply the normal negative-constraint validation and retry/escalation rules, bounded by the initial review-or-gate attempt plus five unsuccessful wave-integration cycles.
8. In `isolated_worktrees`, merge all clean remediation branches into the orchestrator branch. In `same_worktree`, verify the orchestrator-created remediation commits are present. Verify the integrated diff against the negative constraints and rerun required integration gates. When `wave_integrated_review` is enabled, also spawn another fresh full-wave reviewer using the approved next occurrence of that wave's integrated-reviewer coordinate; otherwise spawn no integrated reviewer.
9. Repeat the full-wave remediation loop only through the initial review-or-gate attempt plus five unsuccessful wave-integration cycles. When `wave_integrated_review` is enabled, a fresh matrix-approved integrated review must yield zero orchestrator-validated findings. In either setting, every negative constraint must remain satisfied and all wave gates must pass; otherwise hard-stop on cycle five.
10. Only then mark the full-mode wave accepted, recording whether the independent wave review was clean or `not_run_by_design(wave_integrated_review:false)`, remove its completed run-created worktrees after collecting receipts, and plan/start the next wave. In simple mode, collect the equivalent receipts after step 4 accepts the wave, but keep selected builder threads and their run-created worktrees available through final gates so permitted builder-role continuation remains possible. Remove them during final cleanup.

## Final integrated-task review

After all waves are accepted:

1. Run the repository-defined full gates against the fully integrated task.
2. When `simple_mode` is `true`, spawn no final reviewer or remediation role. On a full-gate failure, identify the responsible slices and resume or reuse their selected builder threads to make verified, in-allowlist repairs under the simple-mode retry rule and the original negative constraints; rerun the full gates after reintegration. If ownership or future execution planning must change, preserve the collision rules and update the deployment-wave matrix before affected work continues. Completion requires orchestrator verification of every negative constraint and all full gates passing. Hard-stop only when an applicable retry limit or another defined terminal condition is reached, and record the final review result as `not_run_by_design(simple_mode)`. When `simple_mode` is `false`, spawn a fresh reviewer using the runtime approved for the final integrated-reviewer coordinate over the entire task, comparing the final branch to the original run base and reviewing requirements, negative constraints, architecture, cross-wave behavior, documentation, security, performance, regressions, and valid nits only within authorized behavior and supported inputs or environments. Existing tests may be used as evidence, but test creation, test modification, and missing coverage are review concerns only when the user explicitly requested tests.
3. Steps 3–5 apply only in full mode. Validate findings using live evidence and the negative-scope contract. Preserve reproducible defects within supported behavior even when their smallest repair is a guard or validation; reject proposed fallback, speculative defensive behavior, or other excluded expansion.
4. Partition validated in-scope findings by exclusive file ownership and run the same matrix-approved remediation fixer/reviewer loop used for wave remediation, including the original negative constraints, approved escalation coordinates after retry 3, and no more than five unsuccessful final-integration cycles after the initial final review.
5. Integrate clean remediations according to `worktree_mode`, verify the final diff against the negative constraints, rerun full gates, and repeat with another fresh whole-task reviewer using the approved next occurrence of the final integrated-reviewer coordinate only through that five-cycle limit. A clean final review, satisfied negative constraints, and passing full gates are required; otherwise hard-stop on cycle five.
6. Full-mode completion requires a clean final matrix-approved integrated review, satisfied negative constraints, and all required repository gates passing. Simple-mode completion requires orchestrator verification of the negative constraints and all required repository gates passing, with no claim that an independent review occurred.

## Receipt discipline

Keep each receipt compact and factual. It only needs to communicate:

- role outcome and resulting commit;
- changed files or findings;
- checks and decisive evidence;
- blockers, if any.

The orchestrator adds run, wave, slice, builder-candidate identity, selection or synthesis verdict, runtime, review-layer, retry, merge, verdict, `selection_source`, `assignment_source`, and cleanup metadata when normalizing the receipt into `receipts.jsonl`.

- Do not reject otherwise usable work because headings, labels, ordering, or formatting differ.
- Do not respawn an agent, restart a phase, roll back a commit, or open remediation solely to repair a report format.
- When a receipt is malformed or incomplete, inspect the live commit, diff, worktree, and checks and reconstruct the facts directly.
